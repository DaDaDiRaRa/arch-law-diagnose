# 정확도·정직성 강화 계획 (arch-law-diagnose)

> 작성 2026-06-29. 이 문서는 **앞으로 할 작업의 상세 계획**이다.
> CLAUDE.md "⏭️ 다음 작업" 섹션에 요약·포인터가 있고, 이 문서가 그 본문이다.

---

## 0. 배경 — 왜 이 계획인가

자매 앱 **arch-law-graph**(법령 지식·RAG·원문 뷰의 주인)와 역할을 나누는 방향을
논의하던 중, 이 앱(diagnose)의 **정체성을 더 날카롭게** 하자는 결론이 나왔다.

- **diagnose = 결정론적 "대지 판정 계산 엔진".**
  출력은 *숫자 + 판정(RED/YELLOW/GREEN) + 근거 조문 포인터(law_refs)*뿐이다.
- **"이 법조문이 무슨 뜻인가"는 절대 직접 생성하지 않고 graph에 위임한다.**
  (그게 환각의 가장 큰 진입점이기 때문.)
- graph가 "지식의 주인"이면, diagnose는 **"검증 가능한 판정의 주인"**이어야 한다.

"날카롭게 한다"의 정확한 의미:

1. 계산이 더 정확해지고,
2. **자기가 모르는 걸 정확히 안다**(= 침묵 과대평가 제로),
3. 법 해석 영역으로 새지 않는다.

## 1. 대원칙 (이 계획 전체의 게이트)

| # | 원칙 | 의미 |
| --- | --- | --- |
| P1 | **기능 유지** | 지금은 MCP/API화·기능 경계 재편을 **하지 않는다.** 있는 기능을 빼거나 바꾸지 않는다. |
| P2 | **추가형 우선** | 지금 단계 작업은 전부 *기존 동작을 0으로 건드리는 추가형*이어야 한다. 신호·점수·답변범위를 바꾸는 건 보류. |
| P3 | **정체성 ≠ 기능 제거** | "정체성을 날카롭게" = *같은 기능을 더 정확하게.* 기능을 빼서 날카롭게 하는 건(예: C) graph가 정식 API로 붙는 그때 일이다. |
| P4 | **환각 표면을 늘리지 않는다** | 정확도를 올린다며 새 추정·새 자동파싱·새 LLM 산정을 들이지 않는다. (§5 "하지 말 것" 참조) |

## 4.5 다음 단계 — 실제 케이스 기반 정확도 캘리브레이션 루프 (미착수, 2026-06-29 추가)

> 골든(D)은 "맞다는 걸 *증명·고정*"한다. 이 단계는 "*틀린 걸 찾아 고친다*" — **엔진 정확도가 실제로 오르는 유일한 경로**.
> 새 구조 신설 아님: 이미 있는 `ordinance_resolver`+`ordinance_seed.json`+`ordinance_extractor` 파이프라인을 **신뢰 가능하게/우선순위 있게** 만드는 일. graph가 못 하는 *대지 판정 정확도* = diagnose 정체성.

### 메커니즘 (캘리브레이션 루프)

```text
실제 케이스 → 엔진에 한도 주입 없이 통과 → 엔진 출력 vs 문서 실제값 대조
  → 어긋나는 지점 = 구체 결함 → 고침(주로 데이터 보강) → 재대조 → 갭 축소(측정 가능)
```

골든은 실제 한도를 stub으로 주입해 *산술만* 검증한다. 주입을 빼고 **엔진 자체 출력**을 실제값과 비교하는 게 출발점.

### 진입점: 법정 한도 재현 감사 (먼저)

- 케이스에 이미 기록된 `context_recorded_not_asserted.legal_*`(legal_bcr/far_pct, legal_parking 등) vs 엔진 **비주입** 출력 대조.
- 산출: "12건 중 N건이 X%p 어긋남" 표 = **pass/fail 골든 아님, 갭 수치화 audit**(조례 도시는 설계상 거의 다 어긋남이 정상).
- 이 표가 곧 "**어느 도시×용도지역 조례부터 채울지**"의 작업 목록.

### 가드레일

- ①의 조례값은 *건축개요 표기*라도 그 프로젝트 특례·완화가 섞였을 수 있으니, **기본 조례값만** 적재하고 가능하면 자치법규 원문 교차확인. 애매하면 적재 말 것.
- ③은 §5 "하지 말 것"의 'LLM이 결정 수치 만들기 금지'와 직결 — 모델링하지 말고 degrade 유지.

### 4.5.1 graph 합칠 때 ①②③이 어디까지 풀리나 (2026-06-29 분석)

> 핵심: **graph는 "조례가 뭐라 하나(기준 데이터)" 절반을 풀고, "그걸 이 대지에 적용·계산·검증"하는 절반은 diagnose 몫.** 합쳐도 데이터 쪽만 풀린다.
> (graph 보유: 전국 84개 *시* × 조례 4종 본문 + 용도지역→건폐율/용적률·주차·이격·조경·인센티브·심의 기준 추출. 로드맵에 `/api/standard?city=&zone=` 엔드포인트 계획됨. ⚠ graph 정보는 작성 시점 기준, 착수 전 재확인.)

| 항목 | graph 합치면 | 이유 |
| --- | --- | --- |
| **① 조례 한도** | **대체로 해결** ✅ | graph가 조례 데이터 주인(84개 시 건폐율/용적률 추출 + `/api/standard` 계획). diagnose는 seed 대신 graph에서 받음 = 역할분담 정확. ⚠ 84개 *시*만(군 미포함·100% 아님), 추출 실패칸 guard, 추출값 정확성은 별도 검증 필요 |
| **② 주차·심의** | **부분** ⚠️ | graph가 *기준 숫자*(주차 조례·심의 대상 임계값) 제공 → diagnose 산정 입력 정확화. 그러나 **산정 로직·트리거 발동(대지 스펙+좌표)·실제결과 대조 검증**은 diagnose만 |
| **③ 완화·정비 인센티브** | **거의 안 됨** ❌ | graph가 완화 *법령 프레임워크*는 주지만, 어려운 핵심(재건축 허용용적률=정비상한·기부채납·지구단위)은 *법조문 lookup이 아니라 정비계획·심의 산물* → 규칙 밖. **환각 위험·"확인필요" 유지 그대로** |

**빠지면 안 될 점**: graph가 조례값을 줘도 *그 추출이 맞는지*는 별개(graph도 regex/LLM 추출 → 오류 가능). 그래서 **실제 케이스로 조례값을 대조 검증하는 §4.5 캘리브레이션은 graph 합치든 안 합치든 필요.** 오히려 **graph=규모(84개 시) / 실제 케이스=정답 검증**으로 상호보완.

**한 줄**: 합치면 ① 거의 해결(graph가 데이터 주인) · ② 데이터 입력만 해결(로직·검증은 diagnose) · ③ 핵심은 안 풀림(규칙 밖). 어느 경우든 캘리브레이션은 별도 필요.

## 5. 하지 말 것 (환각 표면 차단 — 영구 가드레일)

- ❌ **조문 의미 설명·본문 인용을 diagnose가 자체 생성** — graph 영역. 새면 즉시 환각원.
- ❌ **가로구역/고시 PDF 자동 파싱** — 폐지고시 오인·환각 위험으로 이미 보류한 판단을 **유지.** 수동 입력만.
- ❌ **LLM이 결정 가능한 수치(건폐율·용적률·주차대수 등)를 만들게 하기** — 룰 계산은 코드로. LLM은 정성(설비·소방)·요약·보조 의견만(기존 원칙).
- ❌ **점수 곡선([coverage.py:58-68](../backend/services/calculator/coverage.py#L58) 류)을 재설계해 "정밀도"를 흉내** — 임의 휴리스틱을 더 정교하게 보이게 만들면 *가짜 정밀도*가 된다. 점수는 D(골든셋)으로 **캘리브레이션만**, 곡선 자체를 새로 발명하지 않는다.
